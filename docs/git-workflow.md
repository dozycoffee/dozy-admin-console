# Git / 이슈 / PR 워크플로우 규칙

이 문서는 사람 기여자를 위한 안내가 아니라, **이 레포에서 이슈를 만들거나 브랜치를 생성하거나
커밋·PR을 작성하는 AI(Claude Code 등)가 해당 작업을 수행하기 전에 반드시 따라야 할 규칙**이다.
전역 `~/.claude/CLAUDE.md`에도 커밋 형식 규칙이 있지만, 이 문서는 이 프로젝트에서만 적용되는
규칙(이슈 단위 작업, 브랜치 네이밍)을 독립적으로 관리하기 위해 별도로 둔다 — 전역 규칙과 어긋나면
이 문서가 이 레포에서는 우선한다.

## 작업 단위 — 이슈 먼저

- 기능 단위 작업은 코드를 건드리기 전에 GitHub Issue를 먼저 만든다. 오타 수정처럼 사소한 변경이
  아니라면 이슈 없이 바로 브랜치를 파지 않는다.
- `feature_list.json`의 각 항목이 하나의 이슈 단위와 대응된다. 이슈 제목은 해당 항목의 `name`을
  그대로 쓰거나 이해하기 쉽게 다듬어서 쓴다. 이슈 본문에는 `feature_list.json`의 `description`과
  완료 기준을 옮겨 적는다.
- `feature_list.json`에 없는 새로운 작업이 필요해지면(버그 발견, 범위 밖 개선 등) 이슈를 만들면서
  `feature_list.json`에도 항목을 추가한다.

### UI 개선도 이슈 먼저

- 화면 문구·레이아웃·스타일 조정, 모달·툴팁·토스트 같은 **UI 개선도 기능 단위 작업이므로 코드를 건드리기 전에
  이슈를 먼저 만든다.** "작은 UI 수정"이라는 이유로 이슈 없이 시작하지 않는다 — 한 화면을 여러 번 다듬다 보면
  범위가 금방 커져서 나중에 이슈 없이 PR이 쌓이게 된다.
- 이슈 없이 진행할 수 있는 예외는 **오타·문구 한 곳 수정처럼 동작과 구조가 바뀌지 않고 영향 범위가 한두 파일인
  변경**뿐이다. 둘 이상의 화면, 공용 컴포넌트 추가·변경, 사용자 흐름(입력·확인 절차) 변경이 하나라도 있으면
  예외가 아니다. 판단이 애매하면 이슈를 만든다.
- 화면 하나(또는 같은 주제의 화면 묶음)를 고치는 작업은 **이슈 하나**를 먼저 만들고 작업 상세 내용에 고칠 점을
  체크리스트로 적는다. 작업 도중 범위가 늘면 이슈 본문 체크리스트를 갱신하고, 같은 이슈에 PR을 연결한다.
  이슈가 필요한 작업을 이미 진행해 버렸다면 PR을 열기 전에 이슈를 만들어 연결한다(사후 이슈보다 사전 이슈가 원칙).
- 이슈 템플릿은 새 UI·흐름을 만드는 작업이면 `feature`, 동작 변경 없는 정리(스타일·구조 정리)면 `refactor`를
  쓰고, PR 본문의 "연관된 이슈"는 `- Closes #이슈번호`로 쓴다. "없음"은 위 예외에만 쓴다.

## 이슈/PR 템플릿·라벨·타입

- 이슈는 `.github/ISSUE_TEMPLATE/`의 `feature.md`/`bug.md`/`refactor.md` 중 성격에 맞는 템플릿
  구조(섹션 구성)를 그대로 따라 작성하고, 템플릿에 지정된 라벨(`feature`/`bug`/`refactor`)을 붙인다.
  세 템플릿 중 어디에도 맞지 않는 사소한 변경(오타 수정 등)은 이슈 없이 진행할 수 있다(위 "작업
  단위" 절 참고).
- `gh issue create --type`으로 GitHub 네이티브 Issue Type도 함께 지정한다. 매핑은 다음과 같다:
  `feature` 템플릿 → `Feature`, `bug` 템플릿 → `Bug`, `refactor` 템플릿 → 대응 네이티브 타입이
  없으므로 `Task`.
- PR은 `.github/PULL_REQUEST_TEMPLATE.md` 형식(연관된 이슈 / 작업 내용 / 스크린샷(선택) / 리뷰
  요구사항(선택))을 따르고, 연관 이슈와 같은 라벨을 붙인다.
- PR 본문의 "연관된 이슈"는 목록 항목으로 쓴다. `Closes` 앞에 `-`를 붙인다 (예: `- Closes #45`).

## Branch Strategy

- `main` → 기준 브랜치. 모든 작업 브랜치는 `main`에서 분기하고, 완료되면 PR로 `main`에 병합한다.
  `main`에 직접 커밋하지 않는다.
- `feat/[영역]-[기능]` — 기능 추가/변경 (예: `feat/catalog-list-api-integration`)
- `fix/[설명]` — 버그 수정
- `chore/[설명]` — 빌드, 설정, 문서 등 기능 변경이 아닌 작업
- 브랜치 이름은 관련 이슈 번호나 `feature_list.json`의 `id`를 유추할 수 있도록 짓는다.

## Commit Format

```text
<type>(<scope>): <description>
```

| Type | 용도 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 기능 변경 없는 코드 개선 |
| `test` | 테스트 추가 또는 수정 |
| `docs` | 문서 변경 |
| `chore` | 빌드, 설정 등 기타 변경 |
| `perf` | 성능 개선 |

### Commit Rules

- 하나의 커밋에는 하나의 논리적 변경만 포함한다. 관련 없는 변경을 묶지 않는다.
- 커밋 메시지 설명은 "~~한다"체가 아니라 "~~ 추가"처럼 명령문/명사형으로 작성한다.
- 커밋 제목 끝에는 마침표나 기타 구두점을 사용하지 않는다.
- 커밋 본문이 필요하면 각 변경사항을 `-` 단위로 작성한다.
- 테스트가 실패한 상태에서는 커밋하지 않는다. (테스트 러너 도입 전까지는 최소한 `npm run build`,
  `npm run lint`가 통과한 상태에서 커밋한다.)
- 커밋, 이슈, PR 등 어디에도 `Claude-Session` 트레일러 또는 링크를 포함하지 않는다.
- 커밋, 이슈, PR 어디에도 "~하기로 사용자와 확인함", "~로 결정함(사용자 승인)"처럼 작업 중
  누구와 어떤 대화를 거쳐 결정했는지를 서술하는 과정 설명 문구를 쓰지 않는다. 결과(무엇을
  왜 이렇게 했는지)만 적는다 — 의사결정 과정은 세션 대화나 PROGRESS.md에만 남긴다.

## PR 작성 시 확인

- PR 본문에 관련 이슈를 `Closes #이슈번호`로 연결한다.
- PR 본문에도 `Claude-Session` 트레일러/링크를 포함하지 않는다.
- PR을 열기 전 관련 커밋들이 위 Commit Rules를 따르는지 확인한다.
- 화면 변경이 포함된 PR은 `npm run dev`로 직접 확인한 내용을 PR 설명이나 스크린샷으로 남긴다.
- PR을 열기 전, 연결된 이슈의 "작업 상세 내용" 체크박스 중 이번 PR에서 완료한 항목을
  `gh issue edit`로 `- [x]`로 체크해둔다. 이슈를 닫는다고 체크박스가 자동으로 갱신되지 않으므로
  직접 반영해야 한다.

## 추적 문서(feature_list.json·PROGRESS.md) 반영

- 추적 문서 갱신은 작업 PR 안에서 `docs(tracking)` 커밋으로 함께 올린다. 머지 후 문서만 고치는 후속 PR을
  만들지 않는다.
- `feature_list.json`의 `status`는 PR을 열기 전에 완료 기준(build·lint·test 통과, 필요한 브라우저 확인)을
  모두 채웠다면 PR 안에서 `completed`로 바꾼다. 머지가 끝나야 완료로 보는 것이 아니다.
- 브라우저 확인처럼 PR을 연 뒤에야 끝나는 항목이 남아 있으면 `in_progress`로 두고 PR 본문에 미확인으로 적는다.
  확인이 끝나면 머지 전에 같은 PR에 커밋을 추가해 `completed`와 PROGRESS.md 검증 문구를 갱신한다.
