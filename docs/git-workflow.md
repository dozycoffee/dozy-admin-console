# Git / 이슈 / PR 워크플로우 규칙

이 문서는 사람 기여자를 위한 안내가 아니라, **이 레포에서 이슈를 만들거나 브랜치를 생성하거나
커밋·PR을 작성하는 AI(Claude Code 등)가 해당 작업을 수행하기 전에 반드시 따라야 할 규칙**이다.
전역 `~/.claude/CLAUDE.md`에도 커밋 형식 규칙이 있지만, 이 문서는 이 프로젝트에서만 적용되는
규칙(이슈 단위 작업, 브랜치 네이밍)을 독립적으로 관리하기 위해 별도로 둔다 — 전역 규칙과 어긋나면
이 문서가 이 레포에서는 우선한다.

## 작업 단위 — 이슈 먼저

- 기능 단위 작업은 코드를 건드리기 전에 GitHub Issue를 먼저 만든다. 오타 수정처럼 사소한 변경이
  아니라면 이슈 없이 바로 브랜치를 파지 않는다.
- `feature_list.json`의 각 항목이 하나의 이슈 단위와 대응된다. 이슈 제목은 해당 항목의 `name`을
  그대로 쓰거나 이해하기 쉽게 다듬어서 쓴다. 이슈 본문에는 `feature_list.json`의 `description`과
  완료 기준을 옮겨 적는다.
- `feature_list.json`에 없는 새로운 작업이 필요해지면(버그 발견, 범위 밖 개선 등) 이슈를 만들면서
  `feature_list.json`에도 항목을 추가한다.

## Branch Strategy

- `main` → 기준 브랜치. 모든 작업 브랜치는 `main`에서 분기하고, 완료되면 PR로 `main`에 병합한다.
  `main`에 직접 커밋하지 않는다.
- `feat/[영역]-[기능]` — 기능 추가/변경 (예: `feat/catalog-list-api-integration`)
- `fix/[설명]` — 버그 수정
- `chore/[설명]` — 빌드, 설정, 문서 등 기능 변경이 아닌 작업
- 브랜치 이름은 관련 이슈 번호나 `feature_list.json`의 `id`를 유추할 수 있도록 짓는다.

## Commit Format

```text
<type>(<scope>): <description>
```

| Type | 용도 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 기능 변경 없는 코드 개선 |
| `test` | 테스트 추가 또는 수정 |
| `docs` | 문서 변경 |
| `chore` | 빌드, 설정 등 기타 변경 |
| `perf` | 성능 개선 |

### Commit Rules

- 하나의 커밋에는 하나의 논리적 변경만 포함한다. 관련 없는 변경을 묶지 않는다.
- 커밋 메시지 설명은 "~~한다"체가 아니라 "~~ 추가"처럼 명령문/명사형으로 작성한다.
- 커밋 제목 끝에는 마침표나 기타 구두점을 사용하지 않는다.
- 커밋 본문이 필요하면 각 변경사항을 `-` 단위로 작성한다.
- 테스트가 실패한 상태에서는 커밋하지 않는다. (테스트 러너 도입 전까지는 최소한 `npm run build`,
  `npm run lint`가 통과한 상태에서 커밋한다.)
- 커밋, 이슈, PR 등 어디에도 `Claude-Session` 트레일러 또는 링크를 포함하지 않는다.

## PR 작성 시 확인

- PR 본문에 관련 이슈를 `Closes #이슈번호`로 연결한다.
- PR 본문에도 `Claude-Session` 트레일러/링크를 포함하지 않는다.
- PR을 열기 전 관련 커밋들이 위 Commit Rules를 따르는지 확인한다.
- 화면 변경이 포함된 PR은 `npm run dev`로 직접 확인한 내용을 PR 설명이나 스크린샷으로 남긴다.
