# ADR-0003: API 응답 검증 계층으로 Zod 채택

## 상태
Accepted

## 배경 (Context)
이 콘솔은 별도 백엔드 API(dozy-wms-api 등)가 내려주는 응답을 그대로 신뢰해 화면에 렌더링한다.
TypeScript의 타입은 컴파일 타임에만 유효하므로, API 응답 형태가 실제로 타입과 일치하는지는 런타임에
별도로 확인하지 않는 한 보장되지 않는다. 백엔드 스펙 변경이나 예외적인 응답(필드 누락, null 등)이
바로 런타임 에러나 화면 깨짐으로 이어질 위험이 있다.

고려한 대안:
- **응답을 무검증으로 타입 단언(`as Type`)만 사용**: 구현이 가장 빠르지만 런타임 안전성이 전혀
  없고, 백엔드 스펙이 바뀌어도 프런트엔드가 조용히 잘못된 데이터를 렌더링할 수 있다.
- **수동 타입가드 함수 작성**: 검증은 가능하지만 API가 늘어날수록 타입 정의와 타입가드를 이중으로
  유지보수해야 한다.

## 결정 (Decision)
API 응답은 Zod 스키마로 파싱한다. 스키마에서 TypeScript 타입을 추론해 타입 정의와 런타임 검증을
하나의 소스로 유지하고, 파싱 실패는 컴포넌트가 개별적으로 처리하지 않도록 공통 에러 처리 경로로
흘려보낸다. 스키마는 해당 기능의 `model/` 아래 둔다.

## 결과 (Consequences)
- 얻는 것: 백엔드 응답이 예상과 다르면 화면이 잘못된 값을 조용히 렌더링하는 대신 파싱 시점에
  드러난다. 스키마가 타입의 원본이 되어 타입과 검증 로직이 어긋날 일이 없다.
- 감수하는 것: 응답 구조가 바뀔 때마다 스키마도 함께 갱신해야 하는 추가 유지보수 비용이 든다.
- 현재 상태: 의존성은 도입되어 있으나 `httpClient`에 공통 파싱 파이프라인은 아직 연결되지 않았다
  (`feature_list.json`의 `zod-response-validation` 참고). 새 API를 연동할 때 이 파이프라인을 우회해
  각자 다른 방식으로 검증하지 않는다.
- 감사 포인트: `docs/architecture-checklist.md`의 "API 연동" 항목이 이 결정을 근거로 한다.
